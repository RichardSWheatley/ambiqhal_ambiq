# Weaver Scheduler — Patent Search Briefing

**You are a Claude session conducting a prior-art / patentability search
on the Weaver predictive pressure-aware scheduling system.** Read this
file first. It tells you what to search for, what to compare against,
and what to ignore.

## What Weaver actually is (in one paragraph)

A non-invasive scheduling layer for an RTOS (initially Zephyr on Arm
Cortex-M55) that runs above the existing strict-priority dispatcher.
Each tick it computes a Q16.16 fixed-point "pressure" score per
registered thread from three weighted terms (static urgency, observed
buffer-fill, wait-time aging), elevates the highest-pressure
opportunistic ("Weft") thread by adjusting its Zephyr priority, and
suppresses that promotion when a deterministic ("Warp") thread's
deadline is imminent. A TSK fuzzy controller derives a graded
0–255 throttle level from aggregate system pressure with EMA-based
hysteresis so producer threads can self-throttle gracefully. A
follow-on Phase 3 design extends the same model to schedule NPU
inference jobs with an energy budget.

`claude/fixed-point-scheduler-zephyr-RMdbe`, directory
`weaver_scheduler/`.

## What you are searching for

Your job: find patents and published applications that disclose any of
the technical elements below. Flag matches by relevance class (see
"Output format" at the bottom).

### Element A — Predictive pressure-aware thread scheduling

**The combination of:**

1. A fixed-point integer scoring function (Q16.16 in the reference
   implementation) computing per-thread "pressure" as a weighted sum
   of three terms: (urgency × W_u) + (buffer_fill × W_d) + (aging × W_a).
2. **Predictive update**: producer-side helper that stores
   `current_fill + (current_fill − last_fill)`, clamped, so the
   dispatcher acts on projected next-tick state rather than current
   state. Single-step linear extrapolation, integer math.
3. **Saturating-to-MAX Warp threads** that always win the pressure
   tournament without being re-prioritized.
4. **Bounded snapshot dispatch**: per-tick latency is deterministic
   because the registry is a fixed-size array; the math runs lock-
   free on a stack snapshot.
5. **Operates as an additive layer above an unmodified RTOS
   scheduler**, influencing dispatch via standard priority-set calls
   rather than modifying the kernel scheduler.

### Element B — Pre-deadline guard window ("Pattern Slicing")

A scheduling rule that **suppresses opportunistic priority
elevation when a hard-real-time thread's known deadline is within
N ticks**, to give the deadline-bound thread a quiet system and
warm cache lines. The reference implementation calls this the
"pre-Warp guard."

### Element C — TSK fuzzy throttle controller with EMA hysteresis

A graded 0–255 throttle signal generated by:

1. A 0-order Takagi-Sugeno-Kang (TSK) fuzzy controller with three
   linear-membership rules symmetric about a configurable threshold T:
   - LOW (pressure ≤ T/2) → level 0
   - MID (T/2 < pressure < 3T/2) → linear ramp 0..255 centered at T
   - HIGH (pressure ≥ 3T/2) → level 255
2. **A 4-tap EMA on the controller output** to generate hysteresis
   *without* explicit state (the smoothing IS the hysteresis).
3. **Backward-compatible binary throttle**: the existing boolean
   `should_throttle` query returns `level >= 128`, eliminating
   single-tick flap at the threshold boundary.

### Element D — Multi-implementation pressure batch with bit-identical equivalence

Three independently selectable implementations of the per-tick
pressure batch:
1. Pure scalar integer ALU
2. Hybrid: vector load/store + saturating add (touches FPU/MVE
   state) but scalar Q16 multiply
3. Full MVE: true 4-wide Q16.16 multiply via `vmullbq_int_u32` +
   `vmulltq_int_u32` + `vshrnbq_n_u64` + `vshrntq_n_u64`

Selectable at build time, **proven to produce bit-identical results**,
allowing on-target measurement of the lazy floating-point context-
save tax independently from vectorization gain.

### Element E — NPU coprocessor "Loom" arbitration with energy budget

Phase 3 design (header only — `weaver_sched_npu.h` —
implementation deferred):

1. A new thread class ("Loom") representing one neural network
   graph offloaded to an asynchronous fixed-function NPU
   coprocessor (e.g., Arm Ethos-U55).
2. Per-Loom pressure with three terms parallel to the thread
   pressure: input_fill × W_input + output_backlog × W_backlog +
   wait_ticks × W_aging.
3. **Pre-NPU guard**: defers NPU dispatch when CPU hard-real-time
   deadline lands within the expected inference duration.
4. **Per-epoch energy budget**: refresh budget periodically;
   each dispatched inference withdraws `expected_energy_uj`;
   arbiter defers dispatch when remaining budget is insufficient,
   incrementing a deferral counter that producers consume to
   downgrade gracefully.
5. **Three-axis throttle vector** (CPU / NPU dispatch / DMA-IO)
   each with its own TSK fuzzy + EMA, decoupling backpressure
   signals across resource types.

### Element F — Whole-system gestalt

The **combination** of A + B + C + D as an integrated, opt-in,
reversible Zephyr layer for battery-powered wearable workloads on
Arm Cortex-M55 — i.e., the system marketed as "Weaver Predictive
Pressure-Aware Scheduler" — is itself potentially the claim.

## Known prior art (do not re-discover these; compare against them)

You should expect to find these. Read them and **focus on identifying
what Weaver does that they do not**.

1. **Linux Completely Fair Scheduler (CFS)** — proportional-share
   scheduling; computes virtual runtime per task. *Differs from
   Weaver:* CFS is throughput-fair; Weaver is pressure-targeted.
   CFS has no buffer-fill awareness, no deadline anticipation, no
   throttle signal, no NPU coordination.

2. **Earliest Deadline First (EDF) and Rate Monotonic (RM)
   schedulers** — academic real-time scheduling. *Differs from
   Weaver:* EDF/RM operate purely on declared deadlines; Weaver
   adds runtime *state* (buffer fill, aging) as a first-class
   input. Weaver's Warp class is roughly EDF-flavored; Weft is
   not.

3. **iOS/macOS QoS classes** (UserInteractive, UserInitiated,
   Default, Utility, Background) — coarse priority bands. *Differs
   from Weaver:* iOS QoS is static at submission; Weaver is dynamic
   based on observed buffer state.

4. **Android `cpuctl` and `cpuset` cgroups** — CPU bandwidth quotas
   and CPU pinning. Not pressure-aware in the Weaver sense.

5. **Zephyr stock scheduler** — strict priority + optional
   timeslicing among equal-priority preemptible threads. Weaver
   sits *above* this and is intentionally non-invasive.

6. **Zephyr issue #103437** —
   `https://github.com/zephyrproject-rtos/zephyr/issues/103437` —
   proposes per-work-item priority in workqueues. *Different
   subsystem* (workqueue items, not threads) but cites a related
   shortfall of static priority. **Cite this as evidence the
   community recognizes the gap.**

7. **TensorFlow Lite Micro scheduling** — typically sequential,
   one model at a time. No multi-graph arbitration like the
   Phase 3 Loom design.

8. **Arm Ethos-U Driver Stack** — provides command-stream
   dispatch but not energy-budget-aware arbitration across
   multiple graphs.

9. **Apple Neural Engine scheduling patents** (search assignee:
   Apple Inc., classification G06N 3/063) — proprietary; specific
   to ANE; not RTOS-portable.

10. **Patents from Arm Ltd. on Ethos-U integration** — likely
    cover the hardware-software interface; Weaver's Loom layer is
    a *consumer* of such an interface, not a competitor.

## What to ignore (saves time)

- **General hard real-time scheduling textbooks.** EDF, RM, etc.
  are well-known; the patent search is for specific implementations
  matching Weaver's combination of features.
- **Pure machine-learning scheduling.** ML training/inference
  scheduling on data-center hardware is a different domain.
- **Patents about workqueue ordering only.** Issue #103437-style
  references at the work-item layer are a different invention.
- **Power-management patents that don't touch scheduling.** DVFS
  alone is not relevant; DVFS *integrated with pressure-aware
  scheduling* is.

## Important caveats

- **You are not patent counsel.** Do not draft claims, do not opine
  on infringement, do not assess validity beyond informal relevance.
- **Search exhaustiveness matters.** A non-finding does not mean
  novelty; it means *you* did not find it. Document the search
  scope so a human attorney can extend.
- **Date carefully.** Filing-date / priority-date precedes
  publication. A 2024 patent may have a 2022 priority date that
  still blocks novelty.
- **Read the claims, not just the abstract.** Many abstracts
  oversell. Claim 1 is what matters.
- **Check status.** Abandoned applications and expired patents
  still count as prior art, but pending applications with broader
  language are the highest-priority hits.
